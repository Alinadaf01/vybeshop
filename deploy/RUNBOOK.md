## مرحله ۴ — بیلد پنل ادمین، pull ایمیج بک‌اند، بالا آوردن سرویس‌ها

> ⚠️ **این مرحله بازنویسی شد** (`deploy/STAGE4-FIX-TASK.md`). سرور دیگر ایمیج بک‌اند را خودش نمی‌سازد — `playwright install --with-deps chromium` داخل `backend/Dockerfile` از `cdn.playwright.dev` دانلود می‌کند و آن سرویس IP ایران را ۴۰۳ می‌دهد (جیوبلاک عمدی، نه فایروال). به‌جایش، GitHub Actions ایمیج را می‌سازد و به Docker Hub پوش می‌کند؛ سرور فقط pull می‌کند. (اول GHCR امتحان شد، ولی مسیر سرور به آن — پشت Fastly — به‌طور مداوم با TLS handshake timeout شکست می‌خورد؛ Docker Hub قابل‌اتکا کار می‌کند.)

### پیش‌نیاز یک‌باره: توکن Docker Hub

اگر قبلاً نساخته‌ای، یک Docker Hub Access Token بساز:

۱. در Docker Hub: Account Settings → Security → New Access Token
۲. دسترسی را روی **Read-only** بگذار — هیچ دسترسی نوشتنی لازم نیست
۳. توکن را کپی کن (فقط یک‌بار نشان داده می‌شود)

بعد در سرور، داخل `/opt/vybeshop/.env.production` این دو خط را پر کن:

```
DOCKERHUB_TOKEN=<توکنی که ساختی>
DOCKERHUB_USER=<یوزرنیم داکرهابت>
```

### اجرا

```bash
./deploy/setup.sh 4
```

اگر Node.js روی سرور نصب نباشد (لازم برای بیلد پنل ادمین)، اسکریپت همین‌جا با یک پیام روشن متوقف می‌شود، نه با خطای مبهم — دستور نصب را که نشان می‌دهد اجرا کن و دوباره مرحله ۴ را بزن.

اگر خط‌هایی مثل «ورود به Docker Hub — تلاش ۲ از ۵ شکست خورد ... ۲۰ ثانیه صبر» دیدی، **نگران نشو** — لینک این سرور به رجیستری‌ها گاهی کند/ناپایدار است (نه بلاک‌شده)، اسکریپت خودش تا ۵ بار با فاصله فزاینده دوباره تلاش می‌کند. فقط اگر بعد از ۵ تلاش هم شکست خورد و پیام «شبکه به Docker Hub ناپایدار است، چند دقیقه بعد دوباره اجرا کن» را دیدی، چند دقیقه صبر کن و مرحله ۴ را دوباره بزن.

**چه می‌بینی اگر درست بود:** جدول `docker compose ps` پنج سرویس (`db`, `redis`, `web`, `celery-worker`, `celery-beat`) را نشان می‌دهد، همه با وضعیت `Up` یا `Up (healthy)`. `nginx` عمداً اینجا بالا نمی‌آید — پیکربندی‌اش به گواهی SSL نیاز دارد که هنوز نگرفته‌ای؛ مرحله ۶ خودش nginx را بالا می‌آورد. خط «منبع ایمیج بک‌اند» باید با `<DOCKERHUB_USER>/vybeshop-backend` شروع شود — اگر خالی یا چیز دیگری بود، یعنی pull درست انجام نشده.

اگر `web` مدام ری‌استارت می‌شود (`Restarting`)، لاگ چاپ‌شده در انتهای همین مرحله را برایم بفرست.

## بعد از این، آپدیت کد چطور به سرور می‌رسد؟

جریان کار قبلی (تغییر بده، `git pull`، `docker compose up -d --build`) دیگر کار نمی‌کند — سرور نمی‌تواند بک‌اند را بسازد. از این به بعد:

```
۱. کامیت و push به GitHub (از دستگاه خودت)
۲. صبر کن تا GitHub Actions ایمیج جدید را بسازد و به Docker Hub پوش کند
   (در گیت‌هاب: تب Actions → workflow «Build Backend Image» → سبز شود)
۳. روی سرور: اگر می‌خواهی نسخه مشخصی را نصب کنی (نه صرفاً latest)،
   BACKEND_IMAGE_TAG را در .env.production روی همان تگ sha-... بگذار
۴. cd /opt/vybeshop && docker compose --env-file .env.production \
     -f docker-compose.prod.yml pull web celery-worker celery-beat
۵. docker compose --env-file .env.production -f docker-compose.prod.yml \
     up -d web celery-worker celery-beat
```

این فقط برای تغییرات **بک‌اند** (پوشه `backend/`) است. تغییرات پنل ادمین (`admin/`) هنوز مثل قبل روی خود سرور بیلد می‌شوند (`npm run build` — همان چیزی که مرحله ۴ اجرا کرد)، چون پنل ادمین به Chromium نیازی ندارد و روی سرور بیلد شدنش مشکلی ایجاد نمی‌کند.

**بازگشت به نسخه قبل (rollback):** اگر نسخه جدید مشکل داشت، کافی است `BACKEND_IMAGE_TAG` را در `.env.production` به تگ `sha-...` نسخه قبلی برگردانی و مراحل ۴-۵ بالا را دوباره بزنی — نیازی به بیلد دوباره نیست، ایمیج قبلی همان‌جا در Docker Hub مانده.

⚠️ **کشیدن ایمیج از این سرور گاهی چند بار تلاش می‌خواهد — این طبیعی است، نه خرابی.** لینک این سرور به رجیستری‌ها گاهی کند/ناپایدار است (نه بلاک‌شده — تشخیص داده شده که مشکل TLS handshake با تأخیر است، نه رد دسترسی). مرحله ۴ خودش تا ۵ بار با فاصله فزاینده (۱۰، ۲۰، ۳۰، ۴۵ ثانیه) دوباره تلاش می‌کند و هر بار می‌گوید «تلاش N از ۵» — اگر این پیام‌ها را دیدی یعنی در حال کار است، نه هنگ‌کرده. اگر با `docker compose pull` دستی (بیرون از `setup.sh`) هم به همین ارور خوردی، همان کار را بکن: چند بار دستی دوباره امتحان کن، یا چند دقیقه صبر کن.

## قوانین ایمنی که هرگز نباید زیر پا گذاشته شوند

- **هرگز** `docker compose down -v` را روی این سرور اجرا نکن — `-v` تمام volumeها (دیتابیس، media) را پاک می‌کند، حتی اگر نام‌دار باشند.
- اگر مرحله‌ای شکست خورد، **دوباره از همان شماره اجرا کن**، نه از اول — هر مرحله idempotent است.
- اگر مرحله ۵ (انتقال دیتابیس) را دوباره اجرا کنی *بعد از اینکه سایت واقعی زنده شده و سفارش واقعی داشته*، هر سفارشی که بعد از اولین انتقال ثبت شده پاک می‌شود (چون دوباره جایگزین می‌شود). این مرحله فقط برای انتقال اولیه است، نه یک عملیات معمولی.
